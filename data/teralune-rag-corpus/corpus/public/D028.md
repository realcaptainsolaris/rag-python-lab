# Integration deployment

## Separate workspace configuration

Set ORBIT_WORKSPACE_ID explicitly for every deployed sender. Use at most 4 in-flight requests as the initial integration configuration. This is a deployment recommendation, not a replacement for the published workspace request limit.

A credential and a workspace identifier should be deployed as one reviewed configuration change. Changing only the workspace name in a dashboard does not retarget a sender. Check configuration precedence: an environment variable can override the configuration file that an operator edited. Keep the nonsecret effective workspace visible during startup.

Deployment order:

1. Record the effective workspace and client prefix.
2. Deploy the credential with its reviewed scopes.
3. Confirm one accepted write and one readback.
4. Verify the receiver subscription independently.
5. Advance the source checkpoint only from durable acceptance.

## Checkpoint the accepted batch

The checkpoint unit is the acknowledged batch. Persist a source offset only after the sender has durably recorded which items were accepted. If a batch contains rejected items, preserve those items for repair without rewinding every successful item.

A process that commits its source offset before it records the response can lose observations on a crash. A process that never commits can resubmit indefinitely. Store request identity and source identity together so recovery can reconcile either side of a dropped connection.

## Reconnect and observe

Use a reconnect backoff of 30 seconds as the initial setting for a disconnected sender. A persistent authorization error is not a connectivity outage and should not enter an endless reconnect loop.

Observe accepted measurements separately from successful network connections. Add one readback using the intended workspace before enabling alerts or exports. During rollback restore both the credential assignment and target workspace. Rolling back a binary while leaving a newer workspace configuration can preserve the original problem.

## Configuration precedence review

Before rollout, print a nonsecret effective configuration record from the running process. Include the workspace, API prefix, connector version and source checkpoint location. Do not print the credential value. Compare this record with the reviewed deployment configuration rather than assuming that a file on disk is what the process loaded.

A container image, environment file and process supervisor can each provide a different value. If the process supervisor wins, editing the environment file alone will appear ineffective. Restarting an unrelated service can then produce a misleading temporary improvement by changing which sender is active. Trace the actual precedence before making another change.

For a staged rollout, keep the old and new configuration records with their activation times. When an incident crosses the cutover, a request log can be interpreted against the correct target. A single current configuration snapshot cannot reconstruct what an older worker used before it restarted.

## Rollback and source reconciliation

A rollback restores executable code and configuration, but it does not automatically undo accepted observations. Determine the last committed source checkpoint before starting an older sender. If it reads from a previous checkpoint, it may submit records that the new sender already delivered. If it starts too far ahead, accepted-response records that were not committed locally may be skipped.

Use the source identity and durable acceptance record to reconcile the boundary. Avoid changing timestamps or inventing new device identifiers to get the replay accepted. Those changes create a different observation stream and make a later audit harder. A recovery action should preserve what happened at the source.

After rollback, confirm one request in each direction required by the integration. A reader-only smoke request does not prove that the writer has its required scope. Similarly, a successful sender submission does not validate that the downstream receiver or export consumer is using the same workspace.
