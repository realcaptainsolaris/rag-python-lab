# Device registration

## Register by external identifier

Register a device with POST /api/v3/devices. The external identifier is limited to 64 characters and is unique by workspace_id plus external_id. Choose it from the physical inventory, not from an editable display name. Two organisations may use the same local name without sharing a device identity.

Before provisioning a large batch, inspect the identifier normalization performed by your agent. Removing punctuation or truncating identifiers can collapse two inventory entries into one. A display label can be corrected later; changing the integration identity requires a deliberate reconciliation of history.

## Request and response

A registration request identifies the external device and its initial display name. For example:

```http
POST /api/v3/devices
Content-Type: application/json
Authorization: Bearer <ACCESS_TOKEN>

{"external_id":"pump-west-17","display_name":"West circulation pump"}
```

The returned device_id is the identifier used in measurements. Preserve it in the sender configuration. Do not substitute the external identifier for device_id merely because both identify the same physical unit to a human operator. Keep a lookup between the two when integrating with an inventory system.

## Duplicate registration review

If an agent cannot find its device after a reinstall, inspect the workspace before registering another device. The same external identifier in a different workspace is a different registration. A token can be valid while targeting the wrong workspace.

Treat registration as a lifecycle action. Repeatedly creating devices to repair a permission error leaves unused entries and consumes the plan capacity. Confirm the existing identity and scope first, then use the lifecycle procedure to retire entries that were genuinely replaced.
