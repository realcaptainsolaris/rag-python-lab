# Timestamp validation

## Accepted timestamps

Measurement timestamps use RFC 3339 with explicit offset. The service accepts at most 300 seconds of future skew relative to the server clock. A local timestamp without an offset does not establish which instant the sender intended. Convert local device time at the integration boundary and preserve the original clock reading in a separate diagnostic log.

A sample can fail even when its JSON representation is valid. The timestamp must also fall within the workspace retention policy. A connection restored after a long outage can therefore submit structurally valid measurements that are already too old to retain.

## DATA-422 repair

DATA-422 means measurement timestamp outside retention window. Do not replace an old measurement timestamp with the current time just to make it acceptable. That changes the event being recorded and can trigger alerts as if the physical reading happened now.

Check the workspace retention setting, the sender clock and the queued sample age. If the reading is genuinely outside the accepted history, retain it in the source archive according to your own policy. If the device clock was wrong, correct the clock and determine whether historical correction is justified before resubmitting.

## Offset examples

These strings identify the same instant: 2026-03-10T12:00:00Z and 2026-03-10T13:00:00+01:00. The service compares instants, not the displayed hour. A report that groups by local calendar day must make its timezone choice explicit after retrieval.

An agent restart can reset a device clock without resetting the application server clock. Compare device time, sender time and server receipt time separately. Keep the distinction when an incident crosses a daylight-saving transition. A timezone formatting change does not repair a physically incorrect clock.
