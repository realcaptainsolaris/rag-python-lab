# Legacy authentication

## Workspace credentials in 1.8

Orbit 1.8 uses a workspace-wide key for simple integrations. An OAuth access token for this generation lasts 180 minutes. Do not infer token expiry from the API key lifetime. These are separate credential types, even when the same service account owns them.

Assign one owner to each distribution of the workspace key. If ownership changes, inventory every sender before revoking the previous copy. A process can continue running with an old key from an environment variable even after an operator updates a configuration file on disk. Restart or reload the process deliberately and confirm its next request.

## Moving to scoped credentials

The later Orbit 2.4 key model is a scoped API key. Read and write operations can therefore fail independently after a migration. A reader copied into a writing service does not gain write access because the old workspace-wide key used to work there.

When diagnosing a cutover, preserve the credential type as well as the product version in the configuration inventory. A label such as production-key does not identify either. Never compare raw credential strings in an incident document. Compare nonsecret key identifiers and the assigned workspace instead.

## Expiry and client caches

An application should use the expiry returned by the token response. Caching a token for the lifetime assumed by a different generation creates a periodic failure that can look like an intermittent network issue. Renew it before expiry and replace the cache entry atomically.

If one worker refreshes a token while another sends a request, both must use a coherent cache strategy. Avoid replacing a newer entry with an older response from a slow refresh request. This is a client coordination problem; increasing webhook retries does not extend an access token.
